Priority 0 — Fix the correctness issues first

These are more important than adding new strategies.

1. Fix the tail-reachability bug when eating a pearl

This is the biggest issue I see.

Your simulated body intentionally excludes the tail:

for (int i = 0; i + 1 < n; i++)
    world.bodyStamp[cells[i]] = world.bodyGen;

and then reaches_tail() allows the tail itself as the destination.

That is correct for a normal move, because the tail subsequently vacates.

But after eating a pearl, the tail does NOT move.

Your simulation does:

if (!eat0)
    sim.pop_back();

which correctly leaves the tail in the simulated body for an eating move.

However, your occupancy representation still excludes that tail, and reaches_tail() therefore treats it as reachable.

So your logic can effectively say:

"I can reach my tail"

when the tail is actually still occupied by your own body.

Change

Make the simulator distinguish:

tail_moves = true
tail_moves = false

Then:

normal move:
    tail cell may become free

pearl move:
    tail remains blocked

Your flood fill and tail reachability should receive this information.

This will make your "survival invariant" substantially more correct.

2. Rewrite the body reconstruction using get_dir()

Your rebuild_body() currently searches adjacent cells and picks the first matching segment:

for (int d = 0; d < 4; d++)
{
    ...
    if (p && p->get_id() == id && !p->is_head())

This can break when your snake coils, because a segment can have multiple adjacent segments belonging to the same dragon.

You already have the information needed to reconstruct the body exactly:

DragonPart.get_dir()

From the documentation:

head:
    get_dir() = direction the head is facing

body:
    get_dir() = direction toward the next segment/head

So reconstruct the chain using orientation rather than "first adjacent matching segment."

Conceptually:

HEAD
 ↓ opposite(head.dir)
segment
 ↓ opposite(segment.dir)
segment
 ↓
...
TAIL

This eliminates a nasty source of silent state corruption.

3. Build one authoritative simulate_move() function

Right now movement simulation is spread across choose_move(). You have one simulation for the first move and another miniature simulation for depth-2.

That will become dangerous once you introduce sprinting, portals, enemy predictions, etc.

Create something conceptually like:

struct SimState {
    std::deque<int> body;
    int head;
    int tail;
    bool alive;
    bool atePearl;
    int length;
    Direction facing;
};

and:

SimState simulate_step(
    const SimState& state,
    Direction direction,
    WorldState& world
);

It should handle all of:

direction
wrap-around
kelp
portal
self collision
enemy collision
head-to-head
pearl eating
tail movement
facing direction
death

Then make everything else use this simulator.

This is the single most important architectural change before implementing search.

Priority 1 — Replace binary survival with richer topology
4. Add articulation-point / bottleneck detection

Your current philosophy is:

maximize reachable area

which is good, but area alone misses important topology.

Imagine:

        huge area
           |
       one-cell neck
           |
         head

Flood-fill says:

AREA = 300

which looks excellent.

But you're actually sitting behind a single choke point.

Compute whether the current head region contains:

articulation cells
one-cell corridors
dead-end branches
narrow tunnels

Then penalize moving into them.

A useful metric is:

number of independent exits from head region

For example:

1 exit  → dangerous
2 exits → acceptable
3+      → strong

This complements your area metric beautifully.

5. Track "escape options", not just reachable area

Add:

legal_next_moves
legal_2nd_moves
legal_3rd_moves

For every candidate.

For example:

Move A:
    area = 200
    next moves = 3
    depth2 options = 6

Move B:
    area = 210
    next moves = 1
    depth2 options = 1

Your current area objective can choose B.

I would usually prefer A because it preserves mobility.

Use something like:

mobility_score =
    next_moves * 100
  + second_moves * 20
  + third_moves * 5

as a secondary topology feature.

6. Measure body-to-space ratio

Instead of only:

area

calculate:

area / body_length

and perhaps:

(area - body_length) / body_length

A 100-cell region for a length-10 snake is very different from a 100-cell region for a length-80 snake.

This also gives you a much more principled growth governor.

Priority 2 — Fix the growth strategy
7. Remove the hard-coded N / 10 growth cap

You currently have:

int const growthCap = std::max(9, world.N / 10);

and refuse to prioritize growth beyond it.

I don't like this as a final strategy.

The game explicitly rewards the longest living dragon as the first tiebreak, and then total team length as the second. Your hard cap can voluntarily give up that advantage.

Instead, make growth depend on geometry:

Can I eat this pearl AND retain:
    tail connectivity?
    2+ escape options?
    sufficient free area?
    reasonable body/space ratio?

Then:

small constrained region
    → don't grow

large region
    → grow aggressively

huge region with several exits
    → grow very aggressively

In other words:

Don't cap length based on board size. Cap growth based on post-growth survivability.

8. Score pearls by value, not distance

Your pearl_direction() currently prioritizes currently visible pearls and soon-to-spawn pearls using a relatively simple attraction score.

Upgrade this to:

pearl_value =
    growth_value
    × safety
    × accessibility
    × future_value

A pearl should become more valuable when:

very close
+
safe route
+
large open area afterward
+
enemy probably can't reach it first
+
teammates aren't already targeting it

And less valuable when:

route requires entering a corridor
enemy is nearby
eating it freezes the tail
it causes poor topology
9. Predict pearl races between teammates

Right now every dragon basically sees:

"Pearl over there!"

and heads toward it.

Your dispersion system reduces this somewhat, but it doesn't explicitly reserve resources. Your teammate information is currently based on visible friendly segments and distance-based repulsion.

Instead estimate:

my ETA = 7
teammate ETA ≈ 4

Then don't chase it.

Likewise:

enemy ETA ≈ 5
my ETA = 3

means the pearl is strategically valuable.

This turns pearl collection into a resource-allocation problem instead of independent greedy collection.

Priority 3 — Make your multi-dragon system much better
10. Replace permanent ID roles with state-dependent roles

This part needs reconsideration.

You currently calculate:

g_teamSize = C.get_unit_count();
g_teamIndex = (C.get_id() / 2) % g_teamSize;

and initialize it once.

The problem is that split children start a fresh process and therefore have a different initialization state.

So role assignment can become inconsistent:

Parent:
    team size = 4

Child:
    team size = 5

The same ID-based formula now gets interpreted under a different modulus.

Better

Use a deterministic role function:

role = hash(dragon_id) % ROLE_COUNT

but combine that with dynamic state.

For example:

ANCHOR
COLLECTOR
EXPLORER
DEFENDER

and dynamically change roles based on:

length
location
pearl density
enemy proximity
available space

You can still use the ID as a deterministic tie-break.

11. Make the "lead dragon" dynamic

You currently guarantee:

teamIndex == 0 → never split

which is conceptually good.

But a better rule is:

lead = dragon currently best positioned to become
       the longest surviving dragon

For example:

Dragon A:
length = 30
space = 500

Dragon B:
length = 25
space = 200

Dragon C:
length = 20
space = 600

You might want A as current anchor, but C could become the better long-term anchor.

This becomes especially useful after splitting.

12. Coordinate based on heads, not every teammate segment

Your dispersion currently considers every visible friendly body cell.

That's noisy.

A long teammate creates a huge repulsion field despite its head being somewhere else.

Instead calculate:

head-to-head repulsion
+
predicted head destination
+
claimed pearl region

rather than:

distance from every friendly body segment

You will get much more meaningful fleet behavior.

Priority 4 — Start modelling enemies

This is where I think your largest performance jump will eventually come from.

13. Build an enemy-head threat map

For every visible enemy head:

enemy head
     ↓
N / E / S / W
     ↓
possible next positions

Mark those cells:

danger = 1

and perhaps:

danger = 2

for positions reachable by multiple enemy moves.

Then your candidate score becomes:

survival
+
space
+
growth
-
enemy_threat

instead of simply treating the currently occupied enemy body as a wall.

14. Predict enemy movement based on geometry

You don't need machine learning.

You can estimate:

enemy probably prefers:
    pearls
    open space
    avoiding self collision

which are the same broad motivations your bot has.

For each enemy head, calculate its own:

safe directions
reachable area
nearest pearl

from the information you can see.

Then estimate:

P(enemy enters cell)

even crudely.

For example:

enemy can reach X via 3 of 4 safe actions
→ high danger

enemy can reach Y through only one constrained path
→ lower danger

This is much better than binary occupancy.

15. Add enemy length into the threat model

A long enemy snake isn't just another obstacle.

Suppose:

Enemy A = length 5
Enemy B = length 30

and both heads are nearby.

A confrontation with the 30-length snake has much larger consequences because:

its body occupies more space
death releases more pearls
its future movement options differ

Track:

enemy_id
enemy_length
enemy_head
enemy_facing
visible body
last_seen_round

with a confidence value.

Priority 5 — Portals
16. Stop permanently treating portals as walls

Your code deliberately does:

return e.is_passable() && !e.is_portal();

so portals are always rejected.

That is a good initial safety policy, but it leaves a large amount of the map unused.

Once your simulator is correct, implement:

portal A
    ↓
portal ID
    ↓
portal B

and treat the portal transition as a graph edge.

You can then classify:

known portal + known destination
    → usable

known portal + unknown destination
    → risky

unknown portal
    → don't use

This gives you the benefits without sacrificing safety.

17. Use portals strategically for escape

The strongest use of portals may not be pearl collection.

They can provide:

escape routes

Imagine:

enemy blocks west
enemy blocks north
east = dead end
south = portal

Your normal openness heuristic may hate the portal because it can't see through it.

A portal-aware simulator can discover:

portal → huge free region

which completely changes the correct decision.

Priority 6 — Implement sprinting
18. Add sprinting only after you have the exact simulator

Your docs make sprinting extremely interesting:

MOVE NNE

executes three sequential movement steps, with collision and pearl handling at every individual step.

Your current simulator isn't designed for that yet.

Implement:

simulate_sequence(
    {NORTH, NORTH, EAST}
)

and process:

step 1
    collision
    pearl
    body update

step 2
    collision
    pearl
    body update

step 3
    collision
    pearl
    body update

The fact that a multi-step action can produce different results depending on ordering is strategically valuable.

For example:

NNE
ENN
ENE

are different actions even when they approach similar destinations.

19. Use sprinting for tactical escapes

Don't initially use sprinting everywhere.

Candidate use cases:

escape enemy head
reach imminent pearl
cross open region quickly
enter/exit portal
avoid losing a contested resource

A nice strategy is:

normal move = default

sprint only when:
    value(sprint) > value(best normal move) + threshold
Priority 7 — Add search

This is where your existing machinery becomes powerful.

20. Move from heuristic choice → beam search

Your current process is:

generate 4 safe moves
→ evaluate
→ choose max

You can see this in the candidate loop in choose_move().

Instead:

depth 0
   4 candidates

depth 1
   top 3 × 4

depth 2
   top 3 × 4

depth 3
   top 3 × 4

For example:

beam width = 8
depth = 3

means you evaluate perhaps:

4 + 32 + 256

rather than the enormous full tree.

But after pruning dead states, it becomes manageable.

21. Use lexicographic scoring for search

I'd strongly recommend against continuing to pile magic constants onto:

area * 100
+ 200000
+ 20000
...

Your current scoring has several large hand-tuned terms.

Instead define:

Priority 1:
    alive?

Priority 2:
    tail reachable?

Priority 3:
    number of escape routes

Priority 4:
    reachable space

Priority 5:
    enemy danger

Priority 6:
    pearl value

Priority 7:
    team dispersion

You can implement this as a tuple:

struct Score {
    bool alive;
    bool tailSafe;
    int exits;
    int area;
    int threat;
    int pearl;
    int coordination;
};

and compare lexicographically.

This is much easier to reason about.

22. Add transposition caching

Beam search will repeatedly encounter the same geometry.

Hash:

head position
facing
body shape
round

and cache:

evaluation

Even a simple Zobrist-style hash could save a lot of computation.

Priority 8 — Improve pearl prediction
23. Track uncertainty after an expected spawn

Currently you store:

pearlTime
pearlRound
pearlNow

which is a good start.

But once the expected spawn round arrives while the tile isn't visible, you cannot know exactly what happened.

Instead maintain:

next_possible_spawn
earliest_possible
latest_possible
confidence

For example:

observed:
    countdown = 4
    minGap = unknown
    maxGap = unknown

after four rounds:
    spawn should have been attempted

At that point:

state = uncertain

instead of blindly continuing deterministic prediction.

24. Exploit map symmetry

Your documentation says symmetric maps share pearl countdowns.

Your bot currently doesn't seem to make systematic use of that.

Maintain symmetry hypotheses:

mirror X
mirror Y
rotation 180

and eliminate hypotheses that contradict observed information.

Once one survives:

pearl at A
    ↔
pearl countdown at mirror(A)

You can potentially predict important resources outside your vision.

This is especially valuable because your bot already has a full-board pearl memory.

Priority 9 — Sonar
25. I would move sonar from "deferred" to "experimental"

Your code currently has no sonar logic despite the game explicitly providing it. Your own comment lists sonar as deferred.

You don't need a complicated protocol.

Use the 32-bit integer as a packed message:

bits:
0-5    sender ID fragment
6-8    message type
9-14   x
15-20  y
21-23  direction
24-31  payload

Message types could be:

0 = enemy spotted
1 = pearl found
2 = requesting space
3 = target region
4 = danger
5 = role update

The message needn't identify the exact sender perfectly.

The important thing is giving the fleet shared information.

26. Use sonar as information, not control

Don't make your entire strategy depend on communication succeeding.

Good:

"Enemy near (12,7)"

Bad:

"Dragon 7 must execute plan B"

because sonar can be intercepted by an enemy dragon and messages have timing constraints.

Treat sonar as:

bonus information

rather than a required synchronization mechanism.

Priority 10 — Better splitting
27. Replace length >= 18 with a split-value calculation

You currently use:

constexpr int SPLIT_MIN = 18;

and then split approximately in half.

Instead calculate:

value of split =
    expected additional pearl access
    + territory expansion
    + survival improvement
    - loss of anchor length
    - increased collision risk

Then split when:

split_value > no_split_value

This is much stronger than:

I'm 18+ → split
28. Sometimes split asymmetrically

You currently do:

childOut = len / 2;

That's a reasonable baseline.

But consider:

parent = 25
child = 5
parent = 20

instead of:

parent = 13
child = 12

when the purpose is creating a tiny explorer.

For example:

ANCHOR:
    20+

EXPLORER:
    3-7

The explorer can collect pearls or investigate a region while the anchor protects the longest-dragon tiebreak.

That's potentially much more useful than creating two equally large snakes.

Priority 11 — Better team territory strategy
29. Assign regions instead of simple repulsion

Your current strategy says:

"Don't be too close to teammates."

A stronger strategy is:

"Each dragon owns a region."

For example, Voronoi-style:

pearls
   ↓
cluster
   ↓
nearest dragon
   ↓
assigned territory

Each dragon then primarily searches for pearls within its region.

This avoids:

four dragons
      ↓
same pearl
      ↓
traffic jam

while still allowing dynamic reassignment when an enemy appears.

Add:

The architecture I would target

Your v2.1 currently looks approximately like:

              WORLD MODEL
                   ↓
          SAFE CANDIDATES
                   ↓
             FLOOD FILL
                   ↓
           HEURISTIC SCORE
                   ↓
                MOVE

I'd evolve it into:

                  WORLD MODEL
                       │
        ┌──────────────┼───────────────┐
        ↓              ↓               ↓
   Own Geometry   Enemy Model     Resource Model
        │              │               │
        └──────────────┼───────────────┘
                       ↓
                ACTION GENERATOR
                       │
             ┌─────────┼─────────┐
             ↓         ↓         ↓
          MOVE       SPRINT     SPLIT
             │         │         │
             └─────────┼─────────┘
                       ↓
                 STATE SIMULATOR
                       ↓
                 BEAM SEARCH
                       ↓
               LEXICOGRAPHIC
                  EVALUATION
                       ↓
                 BEST ACTION
My recommended order

I would implement the next versions approximately like this:

Version	Main change
v2.2	Exact body reconstruction + exact tail semantics
v2.3	Better topology: exits, bottlenecks, body/space ratio
v2.4	Enemy-head threat map
v2.5	Dynamic pearl valuation + teammate resource assignment
v2.6	Better dynamic splitting
v2.7	Portal-aware simulation
v2.8	Sprint simulator
v2.9	Beam search
v3.0	Sonar coordination + opponent modelling
The three changes I'd attack first

1. Exact simulator.
Your future improvements depend on this. Right now the first thing I would fix is the tail/eating semantics and rebuild_body() ambiguity.

2. Enemy threat modelling.
This is the biggest strategic gap in the current bot. Right now your model of other dragons is primarily "occupied cells + nearby heads." Your code explicitly records visible other segments, but does not maintain a predictive enemy state.

3. Beam search over your existing simulator.
This is where your current architecture starts paying off. You already have the machinery to simulate bodies and flood-fill hypothetical states.
